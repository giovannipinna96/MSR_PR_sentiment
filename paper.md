# Sentiment Analysis of Code Review Friction in AI-Assisted Pull Requests

## Abstract

The integration of AI coding agents such as GitHub Copilot, Devin, Claude Code, and OpenAI Codex into software development workflows has transformed how code is generated and reviewed. However, little is known about the friction these AI-generated contributions create during code review processes. This study presents a comprehensive sentiment and emotion analysis of **11,017 code review items** from **7,156 pull requests** generated by five distinct AI coding agents, sourced from the AIDev dataset and filtered to include only repositories with 100+ GitHub stars, permissive licenses (MIT/Apache-2.0), and meaningful human evaluation before PR closure. Using a multilingual RoBERTa-based transformer pipeline with multi-model validation, BERTopic for topic modeling, and zero-shot classification for friction categories, we investigate four research questions concerning sentiment patterns, agent-specific friction differences, friction-generating topics, and correlations with PR outcomes. Our results reveal statistically significant differences in friction levels across AI agents (Kruskal-Wallis H=560.72, p<0.001, η²=0.051 small effect), with OpenAI Codex generating the lowest friction (M=0.136) and Copilot the highest (M=0.270). Pairwise comparisons with Bonferroni, Holm, and Benjamini-Hochberg corrections and Cliff's Delta effect sizes reveal meaningful differences: Copilot vs OpenAI Codex (δ=0.336, medium effect), Claude Code vs Copilot (δ=-0.235, small effect). Multi-model validation shows substantial agreement between RoBERTa models (κ=0.683). Topic analysis identifies code style issues as the dominant friction category (54.6%). We find significant correlations between friction and both merge success (r=-0.085, p<0.001) and review iterations (r=0.410, p<0.001). These findings provide actionable insights for AI agent developers and software engineering teams adopting AI-assisted development practices.

## 1. Introduction

### 1.1 Background

The emergence of AI-powered coding assistants represents a paradigm shift in software development. Tools such as GitHub Copilot, Anthropic's Claude Code, Cognition's Devin, and OpenAI Codex have demonstrated remarkable capabilities in generating code, fixing bugs, and implementing features autonomously. As these agents become increasingly integrated into development workflows, understanding their impact on collaborative software engineering processes becomes crucial.

Code review serves as a critical quality gate in software development, where human reviewers examine proposed changes before integration. The interaction between AI-generated code and human reviewers creates a unique dynamic that may differ fundamentally from traditional human-to-human code review interactions. Understanding the "friction" in these interactions—defined as negative sentiment expressed during review—provides valuable insights into the challenges and opportunities of AI-assisted development.

### 1.2 Research Questions

This study addresses four research questions:

- **RQ1**: How does review comment sentiment manifest for Agentic-PRs?
- **RQ2**: Are there friction differences across different AI agents?
- **RQ3**: Which specific topics (security, testing, code style, logic) generate the most friction?
- **RQ4**: How do friction metrics correlate with outcomes (rejection, iterations, time-to-merge)?

### 1.3 Contributions

This paper makes the following contributions:

1. A large-scale empirical analysis of sentiment in AI-generated pull request reviews across five major AI coding agents
2. A comparative analysis of friction patterns between inline code review comments and top-level reviews
3. Identification of friction patterns across different PR types (features, fixes, documentation, etc.)
4. Statistical evidence of significant differences in friction levels across AI agents
5. Correlation analysis between friction metrics and PR lifecycle outcomes

### 2.2 Sentiment Analysis

**Model Selection:**

We employ the `cardiffnlp/twitter-roberta-base-sentiment-latest` model for sentiment classification. While this model was originally trained on Twitter data, recent research (2024) demonstrates that transformer-based models consistently outperform domain-specific sentiment analysis tools for software engineering contexts, including SentiCR, Senti4SD, and SentiStrength-SE, by up to 35.6% in F1 scores.

**Friction Score Definition:**

For each review comment or review, we define the friction score as the probability of negative sentiment:

```
Friction Score = P(negative | text)
```

This continuous measure (0-1) captures the intensity of negative sentiment rather than a binary classification, enabling more nuanced statistical analysis.

**Processing:**

- Batch processing with batch_size=32
- Text truncation at 512 tokens (BERT maximum)
- GPU-accelerated inference when available
- Separate analysis for comments and reviews to enable comparative insights

### 2.3 Topic Modeling

We employ BERTopic for unsupervised topic discovery on negative comments, following established best practices:

**Configuration:**

- Embedding model: `all-MiniLM-L6-v2`
- Vectorizer: CountVectorizer with English stopwords, min_df=2, ngram_range=(1,2)
- ClassTfidfTransformer with reduce_frequent_words=True
- Minimum topic size: 5 comments

This configuration ensures meaningful topic representations by:
1. Preserving full context during embedding generation (no preprocessing)
2. Removing stopwords only in topic representation phase
3. Using n-grams to capture multi-word concepts

**Category Classification:**

In addition to unsupervised topic modeling, we employ zero-shot classification using `facebook/bart-large-mnli` to categorize negative comments into predefined friction categories:
- Testing
- Security
- Code Style
- Logic
- Documentation

### 2.4 Statistical Analysis

We employ the following statistical methods:

1. **Kruskal-Wallis H-test**: Non-parametric test for comparing friction distributions across multiple AI agents
   - **Eta-squared (η²)**: Effect size measure calculated as (H - k + 1)/(n - k) to quantify the proportion of variance explained
   - Effect size interpretation: small (<0.06), medium (0.06-0.14), large (>0.14)

2. **Post-hoc Dunn's Test**: Pairwise comparisons when Kruskal-Wallis is significant

   **Methodological Note:** We use Dunn's test rather than Mann-Whitney U for post-hoc comparisons because:
   - Dunn's test uses the **same shared rankings** calculated by Kruskal-Wallis
   - Mann-Whitney U re-ranks only two groups at a time, effectively using **different data** for each comparison
   - Dunn's test incorporates the **pooled variance** implied by the Kruskal-Wallis null hypothesis

   *Reference: Dunn, O.J. (1964). Multiple comparisons using rank sums. Technometrics, 6(3), 241-252.*

3. **Multiple Comparison Corrections**: We apply three correction methods with different properties:
   - **Bonferroni**: Most conservative, controls Family-Wise Error Rate (FWER), p_adj = p × k
   - **Holm-Bonferroni**: Uniformly more powerful than Bonferroni while still controlling FWER (step-down procedure)
   - **Benjamini-Hochberg (FDR)**: Controls False Discovery Rate, more powerful, appropriate for exploratory research

   *Note: Bonferroni becomes increasingly conservative with more comparisons (15 in our case), potentially missing true effects. Holm and BH corrections provide additional perspective.*

4. **Cliff's Delta (δ)**: Non-parametric effect size for pairwise comparisons
   - Interpretation thresholds from Romano et al. (2006):
     - |δ| < 0.147 → negligible
     - 0.147 ≤ |δ| < 0.33 → small
     - 0.33 ≤ |δ| < 0.474 → medium
     - |δ| ≥ 0.474 → large

   *Reference: Romano, J., Kromrey, J.D., Coraggio, J., & Skowronek, J. (2006). Appropriate statistics for ordinal level data. Annual meeting of the Florida Association of Institutional Research.*

5. **Chi-square test**: Testing independence between friction categories and AI agents
6. **Point-biserial correlation**: Assessing relationship between friction and merge outcomes
7. **Spearman correlation**: Evaluating relationships between friction and time-to-merge/iterations

### 2.5 Multi-Model Sentiment Analysis (Robustness Validation)

To ensure robustness and reduce model-specific biases, we employ a multi-model sentiment analysis approach using three transformer models:

| Model | HuggingFace ID | Training Data | Labels |
|-------|----------------|---------------|--------|
| Twitter RoBERTa (Primary) | `cardiffnlp/twitter-roberta-base-sentiment-latest` | 124M tweets | neg/neu/pos |
| Siebert RoBERTa Large | `siebert/sentiment-roberta-large-english` | 15 diverse datasets | neg/pos |
| DistilBERT SST-2 | `distilbert-base-uncased-finetuned-sst-2-english` | Stanford Sentiment Treebank | neg/pos |

**Rationale for Model Selection:**
- **Twitter RoBERTa**: Optimal for short, informal text similar to code review comments
- **Siebert RoBERTa Large**: Best generalization across domains (trained on reviews, tweets, news, etc.)
- **DistilBERT SST-2**: Fast baseline model, enables comparison with different architectures

**Inter-Model Agreement Analysis:**

We calculate pairwise Cohen's Kappa (κ) to quantify agreement between models, using Landis & Koch (1977) interpretation:
- κ ≥ 0.81 → almost perfect agreement
- 0.61 ≤ κ < 0.81 → substantial agreement
- 0.41 ≤ κ < 0.61 → moderate agreement
- κ < 0.41 → fair/poor agreement

High inter-model agreement (κ > 0.6) provides confidence that sentiment classifications are robust and not artifacts of a single model's biases.

**Ensemble Predictions:**

We generate ensemble predictions using majority voting across all three models:
- **Ensemble label** = label agreed upon by majority (≥2/3 models)
- **Confidence** = proportion of models agreeing on the label
- **Unanimous agreement** = all three models assign the same label

*Reference: Landis, J.R., & Koch, G.G. (1977). The measurement of observer agreement for categorical data. Biometrics, 33(1), 159-174.*

### 2.6 Emotion Analysis

In addition to sentiment analysis, we perform fine-grained emotion detection using `j-hartmann/emotion-english-distilroberta-base`, which classifies text into seven emotion categories:
- **Anger**, **Disgust**, **Fear** (negative emotions)
- **Joy**, **Surprise** (positive/neutral emotions)
- **Sadness** (negative emotion)
- **Neutral** (no strong emotion)

We calculate a **negative emotion score** as the mean probability of anger, disgust, fear, and sadness, providing a complementary measure to the sentiment-based friction score.

### 2.7 Confounding Variable Analysis

To isolate the effect of AI agent type on friction, we control for potential confounding variables using multiple linear regression (OLS).

**Potential Confounders Identified:**

| Variable | Rationale | Transformation |
|----------|-----------|----------------|
| **PR Type** | Different PR types (fix, feat, docs) may inherently receive different review tones | Categorical dummies |
| **Source Type** | Inline comments are more critical than top-level reviews | Binary (0/1) |
| **PR Duration** | Longer-lived PRs may accumulate more friction | Log-transformed |
| **Text Length** | Longer comments may contain more criticism | Log-transformed |

**Regression Model:**

```
Friction Score = β₀ + β₁(Agent) + β₂(PR Type) + β₃(Source) + β₄(log Duration) + β₅(log Length) + ε
```

We compare:
1. **Unadjusted Model**: Agent dummies only
2. **Adjusted Model**: Agent dummies + all confounders

The change in agent coefficients between models indicates the degree of confounding. If coefficients remain stable after adjustment, agent effects are robust. Large changes (>20%) suggest confounding was present.

*Reference: Pourhoseingholi, M.A., et al. (2012). How to control confounding effects by statistical analysis. Gastroenterology and Hepatology, 5(2), 79-83.*

### 2.8 Statistical Power Analysis

We perform post-hoc power analysis to assess the reliability of our statistical tests and identify potentially underpowered comparisons.

**Power Analysis for Omnibus Test (Kruskal-Wallis):**

Using ANOVA approximation:
- Convert η² to Cohen's f: `f = √(η² / (1 - η²))`
- Calculate achieved power given n, k groups, and α = 0.05
- Target power: 0.80 (80% probability of detecting a true effect)

**Power Analysis for Pairwise Comparisons:**

For each pairwise comparison:
- Convert Cliff's δ to Cohen's d: `d = 2δ / √(1 - δ²)`
- Calculate power using two-sample t-test approximation
- Identify underpowered comparisons (power < 0.80)

**Sensitivity Analysis:**

We calculate the minimum detectable effect size (MDE) for the smallest comparison, answering: "What is the smallest effect we could reliably detect given our sample sizes?"

*Reference: Cohen, J. (1988). Statistical power analysis for the behavioral sciences (2nd ed.). Lawrence Erlbaum Associates.*

### 3.2 RQ2: Friction Differences Across AI Agents

**Kruskal-Wallis Test with Effect Size:**

The Kruskal-Wallis H-test reveals highly significant differences in friction distributions across AI agents:

- H-statistic: 560.72
- p-value: 4.90 × 10⁻¹²⁰
- **Eta-squared (η²): 0.051** (small effect)
- **Result: Highly significant (p < 0.001) with small practical effect**

**Post-hoc Pairwise Comparisons using Dunn's Test:**

*Methodological Note: We use Dunn's test (not Mann-Whitney U) because it uses the same shared rankings as Kruskal-Wallis, making it the proper post-hoc test. Cliff's Delta thresholds follow Romano et al. (2006): negligible (<0.147), small (0.147-0.33), medium (0.33-0.474), large (≥0.474).*

| Comparison | n₁ | n₂ | p_Dunn | p_Bonf | p_Holm | p_BH | δ | Effect |
|------------|----|----|--------|--------|--------|------|-------|--------|
| Claude_Code vs Copilot | 268 | 5,671 | <0.001 | <0.001 | <0.001 | <0.001 | -0.235 | small |
| Claude_Code vs OpenAI_Codex | 268 | 2,152 | 0.010 | 0.095 | 0.019 | 0.011 | 0.097 | negligible |
| Claude_Code vs Cursor | 268 | 636 | 0.658 | 1.0 | 0.658 | 0.658 | -0.007 | negligible |
| Claude_Code vs Devin | 268 | 2,290 | <0.001 | <0.001 | <0.001 | <0.001 | -0.176 | small |
| Copilot vs OpenAI_Codex | 5,671 | 2,152 | <0.001 | <0.001 | <0.001 | <0.001 | **0.336** | **medium** |
| Copilot vs Cursor | 5,671 | 636 | <0.001 | <0.001 | <0.001 | <0.001 | 0.207 | small |
| Copilot vs Devin | 5,671 | 2,290 | <0.001 | 0.004 | 0.001 | <0.001 | 0.046 | negligible |
| OpenAI_Codex vs Cursor | 2,152 | 636 | <0.001 | <0.001 | <0.001 | <0.001 | -0.088 | negligible |
| OpenAI_Codex vs Devin | 2,152 | 2,290 | <0.001 | <0.001 | <0.001 | <0.001 | -0.268 | small |
| Cursor vs Devin | 636 | 2,290 | <0.001 | <0.001 | <0.001 | <0.001 | -0.151 | small |

**Key Findings:**

1. **Largest effect**: Copilot vs OpenAI_Codex shows δ=0.336 (medium effect per Romano 2006), the only comparison reaching medium effect size.

2. **Claude_Code vs OpenAI_Codex**: Not significant with Bonferroni correction (p=0.095) but significant with Holm (p=0.019), showing the difference between conservative and less conservative corrections.

3. **Claude_Code ≈ Cursor**: No significant difference (p=0.658), both agents show similar moderate friction levels.

4. **OpenAI Codex consistently lowest**: Shows significant differences from all other agents except Claude_Code (with conservative correction).

**Friction by Agent and Source Type:**

| AI Agent | Comments (Mean) | Reviews (Mean) | Difference |
|----------|-----------------|----------------|------------|
| Claude_Code | 0.223 | 0.129 | 0.094 |
| Copilot | 0.267 | 0.191 | 0.076 |
| Cursor | 0.232 | 0.228 | 0.004 |
| Devin | 0.244 | 0.198 | 0.046 |
| OpenAI_Codex | 0.205 | 0.078 | 0.127 |

**Key Finding:** OpenAI Codex shows the largest gap between comment and review friction, suggesting that while inline comments may be critical, top-level reviews are notably more positive for this agent.

**Temporal Evolution:**

Analysis of friction trends over time (January 2025 - July 2025) reveals:
- **Devin**: Shows increasing friction over time (r=0.204, p<0.001), rising from ~0.09 in March to ~0.25 in July
- **Claude_Code**: Exhibits increasing friction (r=0.231, p<0.001), from ~0.07 in June to ~0.16 in July
- **OpenAI_Codex**: Maintains consistently low friction (~0.06-0.09) throughout the period (r=0.141, p<0.001)
- **Copilot**: Shows relatively stable friction around 0.18-0.20
- **Cursor**: Maintains stable friction around 0.22-0.23

## 5. Discussion

### 5.1 Key Findings

**OpenAI Codex's Lower Friction:** OpenAI Codex demonstrates significantly lower friction levels compared to other AI agents (M=0.136 vs Copilot M=0.270). This may be attributed to:
- Training on curated code samples with consistent style
- Integration with environments that enforce style pre-submission
- Selective deployment in projects with clearer conventions

**Copilot's Higher Friction Despite Market Dominance:** GitHub Copilot, despite having the largest market presence (51.5% of data), shows the highest mean friction. The medium effect size versus OpenAI Codex (Cliff's δ=0.336) indicates this difference is not merely statistically significant but practically meaningful. This paradox may reflect:
- Broader deployment across diverse project types
- Use in contexts where other agents aren't attempted
- More aggressive code generation that deviates from project conventions

**Claude Code and Cursor Show Similar Moderate Friction:** Both agents (M=0.176 and M=0.210 respectively) occupy the middle ground, with no significant difference between them (p=0.658).

**Multi-Model Validation Confirms Robustness:** The substantial agreement between RoBERTa models (κ=0.683, 85.8% agreement) provides confidence that sentiment classifications are robust and not artifacts of a single model's biases. The low agreement with SentiCR (κ≈0.11) reflects the domain-specific nature of code review language.

**Code Style as Primary Friction Source:** The preponderance of code style issues (54.6%) suggests AI agents may struggle with project-specific conventions, formatting requirements, and idiomatic patterns. This represents a key opportunity for improvement in AI agent training and customization.

**Testing Generates Highest Intensity Friction:** While code style is most common (54.6%), testing-related feedback shows the highest mean friction score (0.723), indicating that when testing issues arise, they generate particularly strong negative reactions.

**Comments vs Reviews Distinction:** The significant difference in friction between inline comments (25.9% negative) and top-level reviews (13.6% negative) reveals that feedback venue matters. This suggests:
- Line-level feedback is inherently more critical
- Top-level reviews serve a summarizing function
- Analyzing only one feedback type provides incomplete picture

**Strong Iteration Correlation:** The r=0.410 correlation between friction and review iterations is notably stronger than typical effect sizes in software engineering research. This indicates friction is a meaningful predictor of review effort and should be monitored.

### 5.2 Implications

**For AI Agent Developers:**
1. Prioritize code style consistency and project convention adherence
2. Enhance security-aware code generation
3. Consider implementing pre-submission linting and validation
4. Focus on documentation and performance tasks where agents excel
5. Provide customization options for project-specific conventions

**For Development Teams:**
1. Establish clear style guides for AI agent configuration
2. Consider agent-specific review checklists based on identified friction patterns
3. Monitor friction trends as agents receive updates
4. Deploy different agents for different PR types based on friction profiles
5. Analyze both inline comments and top-level reviews for complete picture

### 5.3 Limitations

1. **No Human Baseline:** The AIDev dataset does not include review comments for Human PRs (only PR metadata), preventing direct comparison between AI and human-generated code friction
2. **Temporal scope:** Analysis limited to available data through 2025
3. **Sentiment model domain:** While transformer models outperform SE-specific tools, the model was not fine-tuned on code review text
4. **Causal inference:** Correlations do not establish causality between friction and outcomes
5. **Sample size imbalance:** Copilot dominates the dataset (51.5%), potentially skewing aggregate patterns
6. **PR type classification:** Relies on conventional commit parsing which may misclassify some PRs
7. **Quality filtering:** Rigorous filtering (permissive licenses + meaningful human evaluation) reduced dataset from 40,214 to 7,156 PRs, potentially introducing selection bias toward higher-quality projects

### 5.4 Methodological Strengths

1. **Proper post-hoc testing:** We use Dunn's test rather than Mann-Whitney U for pairwise comparisons after Kruskal-Wallis, ensuring consistent use of shared rankings across comparisons
2. **Multiple correction methods:** We report Bonferroni (conservative FWER control), Holm (more powerful FWER control), and Benjamini-Hochberg (FDR control) to provide nuanced significance interpretation
3. **Effect size reporting:** Cliff's Delta with Romano et al. (2006) thresholds provides practical significance beyond p-values
4. **Transparent threshold documentation:** All interpretation thresholds are explicitly cited with references

## 6. Threats to Validity

### Internal Validity
- Sentiment classification accuracy limited by model capabilities
- Category classification relies on zero-shot inference
- Temporal filtering (1-minute threshold) may exclude some legitimate quick-close PRs
- Statistical testing uses Dunn's test (proper post-hoc for Kruskal-Wallis) with multiple correction methods to ensure robustness

### External Validity
- Results may not generalize to private repositories or different technology stacks
- 100+ stars filter may introduce selection bias toward successful projects
- Focus on English-language comments limits generalizability

### Construct Validity
- Friction score as proxy for review difficulty
- Comment count as proxy for review iterations
- PR type classification based on title/commit conventions

## 7. Conclusions

This study presents a comprehensive analysis of code review friction in AI-assisted pull requests, analyzing **11,017 items** across **7,156 PRs** from five major AI coding agents with rigorous quality filtering. Our findings reveal:

1. **Significant inter-agent differences with effect sizes**: AI agents exhibit statistically significant differences in friction generation (H=560.72, p<0.001, η²=0.051 small effect), with OpenAI Codex producing consistently lower friction (M=0.136) than Copilot (M=0.270). Pairwise comparisons with Cliff's Delta effect sizes confirm these differences are practically meaningful (Copilot vs OpenAI_Codex: δ=0.336, medium effect).

2. **Multi-model validation**: Substantial agreement between RoBERTa sentiment models (κ=0.683) confirms robustness of findings.

3. **Source type matters**: Inline code review comments generate significantly higher friction (25.9% negative) than top-level reviews (13.6% negative), highlighting the importance of analyzing both feedback types.

4. **Code style as primary friction source**: Over half (54.6%) of negative feedback relates to code style issues, suggesting a key area for AI agent improvement.

5. **Testing generates highest intensity friction**: While code style is most common, testing-related feedback shows the highest mean friction score (0.723).

6. **PR type predicts friction**: Style and Revert PRs generate dramatically higher friction than Performance and Build PRs.

7. **Strong outcome correlations**: Higher friction is associated with lower merge probability (r=-0.085), longer merge times (r=0.147), and substantially more review iterations (r=0.410).

These findings contribute to our understanding of AI-human collaboration in software development and provide actionable guidance for both AI agent developers and software engineering teams. As AI coding assistants continue to evolve, monitoring and minimizing friction in code reviews will be essential for their successful integration into development workflows.
